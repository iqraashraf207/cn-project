# Limitations and Future Work

- The measured page-load times are above the textbook model (15% to 30% at 100 and 200 ms, much more at 20 ms). The explanation supported by our data is jitter in the virtual machine (ping maxima of 154 to 466 ms) together with the processing and transmission time that the model ignores. The trend itself (a factor of about 2 between non-persistent and persistent HTTP, linear growth with the RTT, 21 against 1 connections) agrees with the textbook.
- There are only 5 runs per page-load case, so the means have a large uncertainty at 20 ms (standard deviation up to 0.8 s), and the 20 ms results should be read with caution. The larger gap between the proxy with an empty cache and direct persistent HTTP at 20 ms is not explained.
- The ApacheBench runs vary a lot between runs (up to about 4 times), so only the broad conclusion (keep-alive helps) is reliable. The comparison between proxy and server throughput is inconclusive.
- The repeat-visit experiment used one run per visit, so its load times show the pattern but have no error estimate.
- The proxy does not support chunked responses, pipelining, range requests or HTTPS, and it is not a full implementation of the HTTP caching specification (RFC 9111). When several clients request the same missing URL at the same moment, each of them can cause a MISS, because the proxy does not coalesce requests.
- The optional extras of the proposal (packet loss with tc netem loss, bandwidth limits with tc tbf, parallel connections) were not done. We expect that packet loss would hurt non-persistent HTTP more than persistent HTTP, because it needs more handshakes and each handshake can lose a SYN; this is an expectation and not a result.

# Conclusion

We built an HTTP/1.1 web server and a caching proxy on plain TCP sockets, deployed them on a routed topology of two routers and three subnets with delay added by tc netem, and measured page load time, TCP connections per page, requests per second, cache hit ratio and bytes saved by 304 responses. The programs work: an automatic smoke test with 20 checks passes on a fresh clone of the repository, and every experiment has packet captures or log files as evidence.

The measurements confirm the structure of the textbook model. A new connection for every object needed 21 TCP connections, one persistent connection needed 1, and persistent HTTP was about twice as fast (2.71 s against 5.47 s at 100 ms; model ratio 1.91). A warm proxy cache loaded the page in 22 to 35 ms at every RTT, 30 to 206 times faster than direct persistent HTTP, because no packet crossed the delayed link. A conditional GET answered with 304 needed 213 bytes instead of 10,506 bytes. The absolute times were above the textbook prediction, by 15% to 30% at 100 and 200 ms, and ping measurements show that delay spikes in the virtual machine are the main reason.

We learned that connection reuse matters as much in the proxy as in the client, since without the connection pool the proxy was 1.6 times slower on a cache miss. Measurements in a virtual machine need many runs and a measurement of the machine's own timing noise before they can be compared with a model. Further work could add request coalescing and chunked transfer to the proxy, repeat the 20 ms case with more runs on a quieter machine, and test packet loss and parallel connections.
